Ripple Server 生产主备自动切流方案

目标是用轻量主备实现自动接管：保留 SQLite 和 Codex 原生运行时文件，使用网关控制唯一写入口，故障时中断运行中的任务并支持用户重试。

V1 边界 单 active 写入 SQLite 保留在本机 SSD/NVMe NAS 做备份和同步，不做双活共享写盘

整体架构

外部网关负责认证、注入可信用户标识和切流；Ripple Server 只在当前主节点写入本地 .ripple；Codex app-server 作为本机执行面进程，由 Ripple 按用户和任务启动或复用。

自动切流流程

自动化只负责判断主节点不可用、切断旧主入口、启动备用节点、再把网关指向新主节点。旧主恢复后不自动抢回主角色，避免脑裂。

连续健康检查失败

Failover controller 每 5-10 秒检查 /health 和 /v1/health/ready。连续失败 3 次后，判定 primary 不可用。

网关停止转发到旧主

网关将旧 primary 从 upstream 中摘除。这个动作必须先发生，确保后续只有 standby 能接收新写请求。

备用节点使用最新数据提升为主

standby 从本地同步目录或 NAS 最新快照恢复 .ripple，启动 ripple-server，并开始成为唯一写入者。

ready 后网关切到新主

新主通过 ready check 后，网关开始转发请求。旧主即使恢复，也只能人工确认后作为 standby 加回。

数据与职责边界

这版方案保留 SQLite。Ripple 的控制面 SQLite 和 Codex 自己的 runtime SQLite 都作为文件状态保护；不修改 Codex 源码，也不试图改变 Codex 的存储方式。

网关

负责外部入口，不让客户端直接控制用户隔离字段。

  • 认证和鉴权
  • 删除客户端伪造的 X-Ripple-User-Id
  • 注入可信 X-Ripple-User-Id
  • 只转发给当前 primary

Primary 节点

唯一在线写入者，运行 Ripple 控制面和 Codex 执行面。

  • ripple-server 写控制面 SQLite
  • 启动或复用 Codex app-server worker
  • 本机 SSD/NVMe 保存 .ripple
  • 异步同步到 NAS 或 standby

Standby 节点

预装相同运行环境，平时不接写请求。

  • 同版本 ripple-server 和 codex
  • 保留最近同步的数据
  • promote 后成为新 primary
  • 旧 primary 需人工确认后重新加入

需要保护的状态

备份和切换时要把 Ripple 控制面、用户工作区、运行产物和 Codex runtime 状态分开看。只备份 ripple.sqlite 不够。

这版方案承诺什么，不承诺什么

承诺

  • 网关自动切到可用主节点。
  • 任何时刻只有一台机器写 .ripple。
  • SQLite 可继续作为 50 并发左右的控制面存储。
  • Codex 存储保持原样，跟随自然升级。

不承诺

  • 运行中的 Codex job 无损迁移。
  • 两台机器同时 active 写同一份状态。
  • 修改 Codex app-server 源码或存储格式。
  • SQLite 立即迁 PostgreSQL。

预期指标

  • RTO：约 30-90 秒，取决于检查间隔和启动速度。
  • RPO：约等于备份/同步间隔。
  • 失败任务：标记中断，用户重试。
  • 旧主恢复：人工确认后作为 standby 加回。
